# SPEC — `cookbook/bisect-breaking-commit/`

An agent works on a real regression-bisection problem inside a disposable
agent-next sandbox: a test broke and nobody knows when. One sandbox per
suspect commit reposes the fixture repo and runs the suite in parallel, and the
culprit commit is named with the receipts. A judge it cannot fool (a planted
regression + an analytic oracle + a negative control + a parallel-speedup gate)
decides whether the result is right.

## Goal

Given a fixture repo whose history contains exactly one regression (a
whitespace-sensitive parse change), identify the exact commit that introduced
it, evidenced by its neighbours (N−1 passes, N fails), and show that the
parallel sweep beats a single-machine serial baseline by a numeric factor.

## Non-goals

- Real-world VCS forensics: no `git bisect` walk, no binary search, no
  real-repo archaeology. The task is a fixed range of 11 commits.
- Any build system, dependency management, or language runtime beyond the
  stdlib. The fixture is pure Python; the judge shells out to `git` and
  `python3`.
- Naming the *content* of the regression: the judge never reads the diff. It
  checks that the identified commit is the planted one and that its neighbours
  behave as required. A correct commit with a fabricated diff still passes;
  a wrong commit with a perfect diff still fails.
- The parallel-orchestration *mechanism* (threads, subprocesses, sandbox API):
  the artifact is the verdict, not the orchestrator.

## Artifact

A single JSON file (the file graded by `judge/grade.sh <artifact>`) with:

- `identified_commit`: the full SHA of the commit the sweep blames.
- `evidence`: `{"n_minus_1_passes": bool, "n_fails": bool}` — the neighbour
  receipts.
- `parallel_speedup`: measured wall-time ratio `serial / parallel`.
- `serial_seconds`, `parallel_seconds`: the two measurements.
- `sandboxes_used`: number of parallel sandboxes the sweep created.

The known-good example is produced by `run.py` (the one-command run) against
the fixture at the demo's pinned ref.

## Judge gates (`judge/grade.sh <artifact> [--seed N] [--json out.json]`)

All gates are numeric and deterministic. Exit 0 only if every gate passes.

- **G1 oracle**: `identified_commit` equals the planted commit SHA (known to
  the judge from `fixture/make_fixture.py`'s pinned `SEED` and
  `PLANTED_INDEX`). No other SHA is accepted.
- **G2 neighbours**: `evidence.n_minus_1_passes` is `true` AND
  `evidence.n_fails` is `true`. A sweep that cannot produce both receipts
  fails.
- **G3 speedup**: `parallel_speedup >= 3.0`. The ratio is recomputed by the
  judge from the artifact's own `serial_seconds` / `parallel_seconds` fields
  and must match the stored `parallel_speedup` within 1 % (no invented
  numbers).
- **G4 negative control**: the judge re-runs the sweep logic against a
  fixture with the planted commit reverted; the result must be
  `"no regression in range"` — never a commit SHA. This is a property of the
  judge's own oracle, checked once per grade run.
- **G5 determinism**: two `grade.sh` runs with the same seed produce
  byte-identical verdict JSON (excluding `timing`).

## Acceptance oracle (independent of "it ran")

1. **Planted regression**: the fixture's commit at `PLANTED_INDEX` (counting
   from the oldest, 0-based) is the only commit that changes parser behaviour.
   The judge regenerates the fixture from `fixture/make_fixture.py` at the
   pinned seed and compares the artifact's `identified_commit` to the planted
   SHA. A sweep that names a random commit — even one with a matching diff —
   fails G1.
2. **Neighbour receipts**: the judge checks that the commit immediately before
   the planted one passes the suite and the planted commit itself fails. This is
   the analytic definition of "the exact commit that introduced the regression".
3. **Negative control**: with the planted commit reverted, the same sweep
   logic must report `"no regression in range"`. A sweep that always names a
   commit (even when none fails) fails G4.
4. **Speedup**: the parallel sweep must overlap I/O-bound sandbox operations
   (create, clone, exec, kill) across sandboxes. On 2 vCPU the CPU work alone
   caps at ~1.2×; the ≥3× gate is met by overlapping sandbox-lifecycle
   latency, which is the honest physics of parallel sandbox bisection. The
   judge verifies the arithmetic from the artifact's own timing fields.

## Self-test (`judge/selftest.sh`)

- The known-good artifact passes all gates.
- ≥ 5 known-bad single-edit mutants of the good artifact each fail ≥ 1 gate;
  mutants generated by `judge/mutants.py` (one edit each).
- Kill rate ≥ 90 % printed by the self-test; exit non-zero otherwise.
- Determinism: two `grade.sh` runs with the same seed produce
  byte-identical verdict JSON; checked by the self-test on every run.

## Judge-integrity rule

The artifact under test is copied to a temp dir before grading; the judge
compares `sha256` of its own `judge/` tree before and after every grade and
fails closed if anything changed.

## Tools (pinned by `judge/setup.sh`)

- git **2.39.5** (Debian bookworm package, SHA256-pinned download),
  installed idempotently.
- Python 3.10+ (stdlib only) for the judge math.
- No third-party packages, no network access at grade time.
