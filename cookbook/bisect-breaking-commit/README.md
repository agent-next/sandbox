# bisect-breaking-commit

A parser test fails at HEAD and nobody knows when it broke. The demo sweeps a
31-commit synthetic repo (`fixture/make_fixture.py`, seeded, offline) whose
commit 25 plants a whitespace-sensitive regression: the terminator check
changes from `line == END` to `line.strip() == END`, so an indented
`\tENDCASE` is silently accepted and the suite fails. **One disposable
sandbox per suspect commit (20..30)** reposes the fixture, checks out its
commit and runs the suite in parallel; the sweep names the culprit with
N−1-pass / N-fail receipts and the diff, and a judge it cannot fool — which
rebuilds the fixture, re-runs the suite at every commit itself and re-runs the
same sweep on a reverted fixture as a negative control — checks the answer
(`judge/grade.sh`, gates G1–G8 in `SPEC.md`). Parallel sandboxes help because
per-commit cost is latency (clone + suite), not CPU: on 2 vCPU the sweep
measures ~3.9× (good example) to ~7.6× (judge's own re-measure) over the
serial baseline.

## Ask your agent

> The parser test fails at HEAD. Clone
> `cookbook/bisect-breaking-commit/` from this repo, build the fixture repo
> with `python3 -I fixture/make_fixture.py /tmp/fixture`, test commits 20..30
> in parallel (one sandbox each: rebuild the fixture, clone it, check out
> your commit, run `python3 test_suite.py`), and tell me the exact commit
> that introduced the regression and the diff of it. Write the sweep report
> (fields in SPEC.md: identified_commit, identified_index, evidence, diff,
> serial_seconds, parallel_seconds, speedup, sandboxes_used) and iterate with
> `bash judge/grade.sh <report.json> --json /tmp/v.json` until it passes.

The agent designs the report itself in the sandbox and uses the judge as the
feedback loop; `examples/good/report.json` is what a correct answer looks
like, produced by `python3 sweep/local_report.py examples/good/report.json`.

## One-command run

```bash
pip install "git+https://github.com/agent-next/sandbox#subdirectory=cli"
export SBX_API_KEY=<your key>
python3 run.py [--ref main] [--keep]
```

`run.py` creates 11 sandboxes (one per suspect commit) + runs the serial
baseline on the orchestrating machine + the negative control in one more
sandbox, writes `sweep_report.json`, grades it with the judge, and always
kills every sandbox it created, confirming with `sbx list`.

## Measured wall time per step

From the fresh-sandbox runs in `RECEIPT.md` (2 vCPU judge, seed 20261015):

| step | wall time |
| --- | --- |
| `judge/setup.sh` (git already matching the pin) | ~2 s |
| `judge/selftest.sh` (good + determinism + 9 mutants) | ~2 min 50 s |
| `judge/grade.sh examples/good/report.json` | ~31 s |
| sweep, parallel (11 commits, 11 sandboxes) | see `run.py` output |
| sweep, serial baseline (11 commits, one machine) | see `run.py` output |

Numbers for the sweep itself come from `run.py`'s per-step timings on your
key's quota; the good example's local-sweep numbers (39.4 s serial vs
10.1 s parallel = 3.91×) are in `examples/good/report.json`.

## Limits, plainly

- The fixture is synthetic and small on purpose: 31 commits, 400-case corpus,
  2.0 s per-suite settle delay standing in for real-suite I/O. A real repo
  with a compile step would dominate the suite cost and scale the same way.
- The regression is planted and the judge knows it (G3); the demo shows the
  sweep finds it with receipts, not that regressions are always
  whitespace-sensitive.
- The speedup gate compares the sweep's parallel wall against a serial
  baseline of the same per-commit work; it does not claim sandboxes beat a
  32-core machine.
- No `git bisect`: the range is fixed at 11 commits and every commit is
  tested (that is what makes the neighbours evidence airtight).
- Third-party data: none. The fixture is generated by a seeded script
  (`fixture/make_fixture.py`); the only pinned download is Debian's
  `git` 1:2.39.5-0+deb12u3 (`judge/package-sha256.txt`).
