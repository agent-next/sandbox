# SPEC — `cookbook/terminal-task-bench/`

A self-hosted terminal task bench. Ten broken filesystems, ten `task.md`
problem statements, ten verifiers, one agent program, one plain-JSON
leaderboard. An agent works on real system-repair problems inside
disposable agent-next sandboxes — one sandbox per task — and a judge it
cannot fool decides whether each repair is right.

## Goal

Run a 10-task bench where every task is a *broken filesystem* plus a
`task.md` plus a `verify.sh`, the agent is a program that repairs the
filesystem in place, and the judge scores it. The judge must:

1. refuse to pass an untouched filesystem (the negative control scores 0/10),
2. check each repair against an oracle that is independent of "the repair
   script ran" (analytic expectation, reference tool, or spec mask),
3. be deterministic — the same seed gives a byte-identical verdict JSON
   apart from wall times, and
4. produce a leaderboard a user can read: per-task verifier output, pass
   counts and a timing table.

## Non-goals

- **No network at grade time.** Fixtures are generated by a seeded script
  (`fixtures/make_fixtures.py`) from the standard library plus `git`,
  `sqlite3` and `tar`; nothing is downloaded while grading.
- **No real systemd, no real cron daemon, no root-only subsystems.** The
  systemd-unit and cron tasks are checked by parsers and by *running the
  program the unit/entry names*, not by booting anything.
- **Not a general agent benchmark.** The ten tasks are fixed, small and
  scriptable on purpose; the point is that the *harness* (fixtures,
  fanout, verifiers, leaderboard) is real and reproducible.
- **No model is invoked.** The "agent" graded by this demo is a shell
  program (`examples/good/agent.sh` and its per-task solutions). Which
  model drives it is out of scope — this demo grades the bench, not a
  language model.
- **No optimality.** A repair that satisfies the gates scores; there is no
  reward for elegance or for margin beyond the pass rules.
- Wall-clock is reported, not graded beyond the coarse budget gate in G4.

## Artifact

The artifact under test is **one agent directory**, graded by
`judge/grade.sh <agent-dir> [--seed N] [--json out.json]`:

```
<agent-dir>/
  agent.sh                 # optional convenience entry point
  solutions/<task-id>/apply.sh   # exactly one per task id, 10 in total
```

For each of the ten task ids the judge:

1. copies the fixture's pristine broken tree to a scratch dir
   (`fixtures/<task-id>/work/` → `scratch/<task-id>/work/`),
2. runs `bash scratch/<task-id>/apply.sh` with `cwd=scratch/<task-id>`
   and `WORK` set to the absolute path of `work/`, 60 s timeout, and
3. runs `bash fixtures/<task-id>/verify.sh <abs path to work/>`.

`apply.sh` is free to use anything on the image. It is graded only by
whether `verify.sh` then exits 0.

The ten task ids, in bench order:

| # | task id | broken thing | oracle kind |
|---|---|---|---|
| 1 | `wal-repair` | SQLite database with a torn WAL header | analytic expectation |
| 2 | `git-lost-branch` | detached HEAD; a branch tip reachable only from the reflog | reference tool (`git`) |
| 3 | `systemd-unit` | unit file with a duplicate key, wrong `ExecStart`, unknown `User` | reference execution |
| 4 | `perms-maze` | a tool unreadable/unexecutable by an unprivileged user | reference execution + spec mask |
| 5 | `csv-normalize` | dirty CSV (CRLF, ragged rows, quoted junk) | analytic expectation |
| 6 | `json-config` | config with duplicate keys, trailing comma, wrong types | spec mask + invariant |
| 7 | `symlink-maze` | a symlink cycle and a dangling link | analytic expectation |
| 8 | `tar-restore` | an archive to restore per a manifest | analytic expectation |
| 9 | `bugfix-python` | a module with a boundary bug; the shipped test is incomplete | independent test |
| 10 | `cron-repair` | crontab entries that no scheduler would accept | spec mask (field expansion) |

## Judge gates

All gates are numeric and deterministic. `grade.sh` exits 0 only if every
gate passes. The verdict JSON carries one `gates` object and one `tasks`
array.

- **G1 solve count.** `solved >= 8` of 10, where a task is solved iff its
  `verify.sh` exits 0 within its timeout. The headline bench bar: an agent
  may miss two tasks and still "solve" the set.
- **G2 no false pass on an untouched tree.** For every one of the ten
  tasks, `verify.sh` run against the *pristine* fixture tree must exit
  non-zero. A single task whose verifier accepts the broken tree fails
  this gate: the bench is worthless otherwise. (Checked every run, not
  only in the self-test.)
- **G3 negative control.** A `true`-only agent built by the judge itself
  (`judge/negctl.sh`, 10 × `apply.sh` containing only `true`) must score
  **0/10** under the same code path. This is the sabotage control: if any
  verifier can be satisfied by doing nothing, G3 fails.
- **G4 budget.** Total verifier wall time across the ten tasks
  `<= 300 s` on 2 vCPU (the per-task `apply.sh` timeout is 60 s). Bounds
  the bench so it stays usable; the timing table is reported either way.
- **G5 determinism.** `grade.sh` run twice with the same `--seed` produces
  byte-identical verdict JSON with the `timing` key removed. (`selftest.sh`
  enforces this; `grade.sh` itself only reports.)

Every gate failure prints the offending task id and the observed number.

## Acceptance oracle (independent of "the tool ran")

Each task's verifier compares against something that is *not* the repair
script's own exit status. The mapping is fixed:

- **Analytic expectation** (`wal-repair`, `csv-normalize`, `symlink-maze`,
  `tar-restore`): the fixture generator writes the intended post-repair
  state as literals — row counts, a canonical dump's sha256, resolved
  paths, per-file sha256 and modes. The verifier compares the repaired
  tree against those literals. Nothing is accepted because "a command
  succeeded".
- **Reference tool** (`git-lost-branch`): the verifier asks `git` itself —
  `rev-parse` of the branch and of its tree against recorded SHAs,
  `symbolic-ref HEAD`, and an empty `git status --porcelain`. `git` is the
  reference implementation, so this is a tool cross-check, not a
  self-report.
- **Reference execution** (`systemd-unit`, `perms-maze`): the verifier
  *runs the program the repaired artifact names* — `ExecStart`'s binary
  with `--self-test`, and `bin/run.sh` as the unprivileged user — and
  compares stdout against a literal. A unit file that merely parses is not
  enough; the thing it points at must work.
- **Spec mask** (`json-config`, `cron-repair`, and the "nothing got worse"
  half of `perms-maze`): a documented numeric predicate over the repaired
  file, independent of how it was produced — weights summing to 100 with
  unique ids; every cron field expanding to the exact expected value set
  under the documented syntax; no world-writable path anywhere in the tree.
- **Independent test** (`bugfix-python`): the verifier carries its own
  test, written against the module's documented contract and covering a
  boundary the *shipped* test does not. The shipped test passing is not
  the oracle.

### Spec masks deliberately not stated in `task.md`

Two tasks carry a check the problem statement does not enumerate, so that a
repair aimed only at the obvious symptom still fails:

- `wal-repair`: the WAL also carries committed rows for an `audit` table.
  `task.md` names the `orders` table only; the verifier requires both.
- `perms-maze`: `task.md` asks for the tool to run as the unprivileged
  user. The verifier also requires that no path in the tree is
  world-writable, which rules out the `chmod -R 777` non-repair.

This is the mask idea from the standard: the oracle measures the *intent*
(committed data recovered, least privilege preserved), not the words.

## Determinism contract

- Every fixture is generated from `--seed` (default `20261015`) by
  `fixtures/make_fixtures.py`; two runs with the same seed produce
  byte-identical trees (fixed commit dates and author identity for git,
  fixed mtimes inside the tarball, no timestamps written into fixtures).
- `grade.sh` sorts its `tasks` array by task id, so parallel execution
  order never reaches the verdict.
- The only non-deterministic field is `timing` (per-task and total wall
  seconds). `selftest.sh` strips it and requires the rest to be identical.
- `--seed` changes fixture *content* only (row counts, names, ordering).
  Gates G1–G4 hold for every seed; the self-test checks a second seed to
  prove the verifiers are not tuned to one fixture instance.

## Self-test (`judge/selftest.sh`)

1. The known-good agent (`examples/good/`) passes every gate.
2. The negative control scores exactly 0/10 (G3).
3. Every pristine tree fails its own verifier (G2), re-checked here.
4. `>= 5` known-bad agents, each a **scripted single-edit mutant** of the
   good agent (`judge/mutants.py`), each fails — kill rate `>= 90 %`.
   A mutant is killed when the task its edit targets no longer passes, so
   a single wrong repair cannot hide behind the 8/10 headline bar.
5. Two `--seed 1` runs of `grade.sh` are byte-identical after removing
   `timing`.
6. A second seed (`--seed 7`) still passes G1–G4 with the good agent.

Exit non-zero if any of the six steps fails.

## Reproducibility tolerances

`RECEIPT.md` records two fresh-sandbox runs. Accepted differences between
them: wall times (any), and nothing else — verdict JSONs must match
byte-for-byte after removing `timing`. If a number differs, that is a bug,
not a tolerance.

## Third-party inputs

None. Every fixture byte is produced by `fixtures/make_fixtures.py` from a
seed; the tools the judge installs are pinned Debian packages with sha256
in `judge/setup.sh` and are recorded in `judge/VERSIONS.txt`. No
third-party dataset, and therefore no third-party licence, is involved.
