# Simulation demo standard

Every simulation demo in `cookbook/` shows one thing: **an agent works on a real engineering problem inside a disposable agent-next sandbox, and a judge it cannot fool decides whether the result is right.** A user can run it in one command and read every result.

## Layout (`cookbook/<name>/`)

| path | what |
|---|---|
| `README.md` | one paragraph on what is simulated and why a sandbox helps; the **"Ask your agent"** prompt for plugin users; the **one-command run**; measured wall time per step; limits stated plainly |
| `SPEC.md` | goal, non-goals, the artifact the agent produces, judge gates with numeric pass rules, the acceptance oracle |
| `judge/setup.sh` | installs pinned tools idempotently into `$HOME` (exact versions; sha256-checked downloads; no `latest`, nothing published in the last two weeks) |
| `judge/grade.sh <artifact> [--seed N] [--json out.json]` | runs every gate, prints one JSON verdict, exits 0 only if all gates pass |
| `judge/selftest.sh` | proves the judge can fail: the known-good example passes; every known-bad example fails at least one gate; prints the kill rate; exits non-zero otherwise |
| `examples/good/` | a known-good artifact (written by hand or from a cited public source with licence) |
| `examples/bad/` or `judge/mutants.py` | ≥ 5 known-bad artifacts, generated by a script where possible (single-edit mutants of the good one) |
| `run.py` | the one-command run for users (below) |
| `media/` | figures + short video, see Media below |
| `media/result.json` | one manifest (`agent-next/result@1`, schema in `cookbook/tools/result.schema.json`) driving the in-chat result card, the demo gallery and the storyboard with the same numbers; written from the grade JSON, checked with `python3 cookbook/tools/result.py check` |
| `REPRODUCE.md` | independent reproduction by a different agent, see Reproducibility |
| `RECEIPT.md` | real command output from two fresh sandbox runs: setup/selftest/grade exit codes, kill rate, key numbers, wall times, tool versions; a "Deviations" section |

## The one-command run (`run.py`)

- Python 3.10+, standard library only. Needs the `sbx` CLI (`pip install "git+https://github.com/agent-next/sandbox#subdirectory=cli"`) and `SBX_API_KEY` (or `E2B_API_KEY`) in the environment.
- Steps: `sbx create --timeout-min 30` → in the sandbox `git clone --depth 1 -b <ref> https://github.com/agent-next/sandbox` (default ref `main`, `--ref` flag to override) → `judge/setup.sh` → `judge/selftest.sh` → `judge/grade.sh examples/good/...` → print the verdict JSON and a short human summary → **always** `sbx kill` in a `finally` block, then confirm with `sbx list` that the id is gone. Non-zero exit on any failure, naming the sandbox id if cleanup could not be confirmed.
- `--keep` leaves the sandbox up and prints its id for exploration.
- Prints wall time per step.

## Judge rules

- Numeric, deterministic pass rules. A gate that "always produces a result" (e.g. a solver run) is not a judge by itself: compare against an analytic solution, a reference tool, a convergence check, or a measured spec mask.
- The self-test is mandatory and must show the judge failing on bad inputs. A judge whose kill rate is below 90 % is not done.
- Never let the artifact under test modify the judge (run it in a copy, compare checksums of `judge/` before and after).

## Reproducibility (required)

A demo is done only when someone else gets the same numbers from the README alone.

- **Pinned everything:** exact tool versions, sha256 for every download, pinned pip versions in `judge/requirements.txt` (with hashes where pip supports it), git SHAs for any cloned source. `judge/VERSIONS.txt` records what `setup.sh` actually installed (`--version` output of each tool).
- **Deterministic:** every random choice takes `--seed`; solvers run single-threaded or with fixed thread counts where results depend on it. `grade.sh` run twice with the same seed gives byte-identical verdict JSON (excluding wall-time fields, which live under a `timing` key). `selftest.sh` checks this.
- **Fresh-sandbox reproduction:** RECEIPT.md has two runs from two *fresh* sandboxes (setup from nothing): both verdicts and key numbers listed side by side; any difference explained or fixed.
- **Independent reproduction:** before merge, a different agent (different model family from the builder) follows only README.md in a fresh sandbox and records its numbers in `REPRODUCE.md`; numbers must match the RECEIPT within the tolerances stated in SPEC.md.
- **Outputs traceable:** each figure and number in README/RECEIPT names the command and seed that produced it.

## Media (`cookbook/<name>/media/`)

Each demo ships what a visitor needs to *see* the result without running anything. The bar for `demo.mp4` is a clip that stops a muted scroller, not a paper figure:

- `media/result.png` — the key figure with the judge's pass line drawn on it (e.g. Bode plot against the spec mask, velocity profile against the analytic curve, step response inside the spec envelope, S11 against -10 dB, stress field with the allowable). Axis labels with units, a title, legend, 200 dpi, readable at 1200 px wide; colour-blind-safe palette.
- `media/loop.png` — the agent loop: judge score or error per iteration until pass (from the grade JSON history), plus the self-test kill-rate bar (known-good vs each known-bad).
- `media/STORYBOARD.md` — the planned storyboard as a filled-in slot table (what fills the frame, the source data/command for each shot, the caption text) written before the video is cut; the video is judged against it.
- `media/demo.mp4` — 16:9 master at >= 1920×1080 (4K hero renders encouraged), 25–60 s, 30 fps, H.264 web encode (`-crf 18 -preset slow -pix_fmt yuv420p -movflags +faststart`) made from a lossless master (`-crf 0`) that `make_media.sh` also writes but git ignores (`media/master/`). Rendered headless with ffmpeg. Under 8 MB. Storyboard slots, in order:

  - **0–2 s — hook:** the finished real result fills the frame. No title card, logo, terminal, or blank chart.
  - **2–10 s — input -> output:** the prompt, spec or photo beside the result it produced.
  - **10–35 s — escalate:** camera moves, close-ups, the result stressed — plus a sped-up process run of the agent in the sandbox, labelled "Nx speed".
  - **then — proof:** the judge PASS verdict and the mutant kill matrix as a HUD overlay on the still-moving result, large enough to read on a phone — never a text slide.
  - **last 2–3 s — end card:** the one-line launch (`python3 run.py` / the "Ask your agent" prompt) on a static frame.

  Craft rules: real animation, not slides. Every shot before the end card is moving real output — a simulation playing, a camera orbiting the model, a render converging, a waveform sweeping, the agent's screen recording; numbers and captions ride on top of it as a HUD. No text-only frames, slide decks, static screenshots or Ken-Burns pans over stills; only the end card is static. Make the clips first (`media/clips/*.mp4`, from the simulator, renderer or browser at 30 fps), then cut them. At least 0.8 scene cuts per 10 s. Burned-in captions readable on a phone — cap height >= 4 % of frame height; terminal captures are cropped/zoomed to the active region. Engineering demos animate the physical thing (tank level, deforming part, waveform, flow particles) — not only plots of it. Every frame is real output from the pinned run; speed-ups are labelled; every number on screen traces to a RECEIPT command.
- Robot, physics and 3D-simulation demos: `demo.mp4` and the hero still in `result.png` are the simulator's own 3D render (e.g. MuJoCo `mujoco.Renderer` offscreen) of the exact trajectory the judge graded, with numbers and the pass line overlaid on the real frames. A matplotlib plot, stick figure or 2D drawing of the motion is not acceptable for these demos.
- `media/REVIEW.json` — the two blind judge verdicts on `demo.mp4` (see Review panel).
- `media/MANIFEST.json` — for each file: what it shows, the command that produced it, the source data file, sha256.
- `media/make_media.sh` — regenerates every file from the judge outputs; the media must be reproducible, not hand-edited.

Figures show measured numbers only — never illustrative or invented data.

`cookbook/tools/video_gate.py <demo.mp4>` mechanically checks the file-level rules above: >= 1920×1080 at 16:9, 25–60 s, 30 fps, H.264 yuv420p with faststart, <= 8 MB, a first frame that is not dark or a solid colour, >= 0.8 scene cuts per 10 s, at least 20 % of the frames before the end card moving (frame-to-frame luma difference >= 1.0 at 640 px wide; slide decks and Ken-Burns stills score ~0 %, viral X demo videos median 49 %), and a static end card in the last 2 s. Caption size, hook content and the storyboard slots are judged by the review panel. A demo whose video fails the gate or the review panel is not done.

`demo.mp4` is produced by the Remotion template in `cookbook/tools/remotion/`: demos write `media/props.json` (shot list, HUD numbers, verdict, launch) and run `render_demo_video.sh media/props.json media/demo.mp4`, which renders headless and fails if the gate fails. Props shape and headless setup: `cookbook/tools/remotion/README.md`.

## Launch

The README's one-command path is the product. An agent with no context beyond `README.md`, starting in a fresh sandbox, must reach the hero result by following only the README. Record the measured time-to-result in `RECEIPT.md` (target: < 5 min on CPU, < 10 min on GPU). If the run needs a hint that is not in the README, the README is wrong — fix it, don't annotate around it.

## Review panel

Two vision models from different families judge `media/demo.mp4` blind — no README, no repo context — using `cookbook/tools/video_review_prompt.md`, scoring 1–10. Pass = both judges score `visual_quality_1_10` >= 8, `wow_1_10` >= 7, `clarity_1_10` >= 7, report `payoff_visible_by_s` <= 2, and `understandable_muted` true. Store both raw JSON verdicts in `media/REVIEW.json`.

## Public-repo hygiene

This repo is public. No hostnames other than public `*.agent-next.com` endpoints, no internal paths, no keys or key-shaped placeholders (write `<your key>`), no internal plans, no names of people. Third-party code keeps its licence file and is cited with URL + version/SHA.

## Size

Keep commits small. No tool tarballs, build trees, meshes over 1 MB, or result dumps in git; `.gitignore` them. Commit the small result numbers in RECEIPT.md instead.
