# gpu-lora-finetune: LoRA fine-tuning demo — SPEC

An agent works inside a disposable sandbox on the most common GPU sandbox use
case: fine-tuning a small open LLM with LoRA on a synthetic format task. The
judge never accepts "training ran": it regenerates the held-out test set with
its own seed, loads the submitted adapter into the pinned base model, scores
exact-match accuracy against the analytic oracle, checks the recorded loss
curve, and verifies the adapter file is real. A sandbox helps because a
fine-tuning run pulls a model hub download, a pinned ML stack and real GPU
VRAM — then needs to be destroyed afterwards.

## Goal

- Artifact: a directory containing `adapter/adapter_model.safetensors` (a real
  PEFT LoRA adapter over the pinned base model), `adapter/adapter_config.json`,
  `metrics.json` (training loss curve + accuracy summaries) and `predictions.csv`
  (held-out inputs with the fine-tuned model's normalized outputs). It must
  pass every judge gate below.
- Judge: `judge/grade.sh` with numeric, deterministic pass rules, runnable
  unchanged on CPU-only machines (the grading path needs no GPU; the training
  path does — see GPU path below).
- Self-test: `judge/selftest.sh` proves the judge fails known-bad artifacts
  (adapter not applied at eval, regenerated test set mismatch, shuffled
  predictions, empty adapter, train-set leakage, no loss decrease, truncated
  training).

## Non-goals

- Beating a published accuracy number; the task is synthetic and fully solved
  by the task generator the judge also uses.
- Multi-GPU training, 4-bit quantization, distributed or federated training,
  model merging into a full checkpoint, or uploading the adapter anywhere.
- Verifying on a CPU-only machine that training *would* succeed on a GPU; the
  CPU judge path checks artifact validity, oracle agreement and gate rules.
  The training run itself is only executable on a GPU lease (see GPU path).

## The artifact contract

`grade.sh <artifact-dir>` grades a directory (or a `.tar.gz`/`.zip` archive of
one) with:

| file | what |
|---|---|
| `adapter/adapter_config.json` | PEFT LoRA config: `r`, `lora_alpha`, `lora_dropout`, `target_modules` list, `task_type`, `base_model_name_or_path` matching the pinned base id, `peft_type` = `LORA` |
| `adapter/adapter_model.safetensors` | non-empty safetensors LoRA weights loadable by the pinned peft, tensors matching `target_modules` |
| `metrics.json` | `losses` (ordered list of floats, first/last recorded), `train_accuracy`, `baseline_accuracy`, `finetuned_accuracy` (claimed, for the record) |
| `predictions.csv` | `input,prediction` rows, one per held-out example in test order, normalized string answers |

## Task definition (fixed)

Synthetic date normalization to ISO 8601. Input: a date in one of several
verbatim templates (below); output: `YYYY-MM-DD`. Generated by a script with
a `--seed` so the judge can regenerate the exact test set independently.

Templates (month names are English, fixed spelling):

1. `March 3, 2024`
2. `3 March 2024`
3. `03/03/2024` (MM/DD/YYYY)
4. `2024-03-03` (already ISO — included so a model can partly shortcut; the
   accuracy gate is set so the baseline still clears it only with LoRA on
   the hard templates)
5. `Mar 3, 2024` (abbreviated month)
6. `3rd of March, 2024` (ordinal day)

Dates span 1990-01-01..2029-12-31 with seeded uniform sampling over the valid
calendar dates. Train: 2000 examples, held-out test: 200 examples, disjoint by
construction (different seed offsets, plus a judge-side dedup check).

## Baseline

The pinned base model zero-shot, scored by the same judge on the same
generated test set: it answers the ISO template (4) exactly and fails the
others, giving baseline accuracy ≈ 200 × (1/6) ≈ 33.3 % (the exact number is
measured, not assumed). The judge computes this itself by running the
pipeline's baseline eval (no adapter).

## Judge gates (numeric pass rules)

`judge/grade.sh <artifact> [--seed N] [--json out.json]` exits 0 only if every
gated pass rule holds. `--seed` (default 0) drives every stochastic step
(test-set regeneration, baseline sampling), keeping verdicts deterministic.
The artifact is graded from a copy in a fresh temp dir; sha256 checksums of
`judge/` before and after must match, else the run fails.

1. **structure** — all four artifact files exist; `adapter_config.json` is
   valid JSON matching the pinned base id and `peft_type=LORA` with a
   non-empty `target_modules`; the adapter file parses as safetensors, is
   ≤ 64 MiB, and its tensors' names/shapes are consistent with the LoRA
   config; `metrics.json` is valid JSON with a numeric `losses` list
   (length ≥ 8) and the accuracy fields; `predictions.csv` parses with
   exactly 200 `input,prediction` rows and every prediction matches the ISO
   regex `\d{4}-\d{2}-\d{2}` with a valid calendar date.
2. **leakage** — the judge regenerates the held-out test set with its own
   seed (independent of the artifact): no `predictions.csv` input may equal a
   train-split input, and every `predictions.csv` input must exactly equal the
   judge-regenerated test input at the same row index (set+order match, not
   just set). Any mismatch fails this gate — this is what kills "eval on the
   train split" and "predictions shuffled".
3. **accuracy (oracle-scored)** — the judge loads the pinned base model and
   the submitted adapter with the pinned peft, generates predictions on the
   regenerated test set with fixed decoding, and computes exact-match accuracy
   against the known correct ISO answer for each input (the generator's
   inverse — an analytic oracle the judge computes itself). Pass:
   `finetuned_accuracy ≥ baseline_accuracy + 0.30` AND
   `finetuned_accuracy ≥ 0.90`.
4. **adapter control** — the identical eval re-run with the adapter detached
   must score ≤ `finetuned_accuracy − 0.30`: the measured gain is
   attributable to the submitted adapter, not to the eval pipeline. Kills an
   artifact whose adapter contributes nothing (e.g. eval hardcoded, or a
   checkpoint that only works when the loader silently falls back).
5. **loss curve** — recorded `losses` are finite floats, `last ≤ 0.5 × first`
   (monotone-ish: also require no single epoch-to-epoch increase > 0.5), and
   `len(losses) ≥ 8`. This is a recorded-evidence check; it is corroborated
   by gates 3–4 actually holding on a regenerated test set.
6. **adapter file real** — `adapter_model.safetensors` non-empty (> 1 kiB),
   contains ≥ 2 distinct LoRA tensor name prefixes (`lora_A`, `lora_B`), and
   loads through the pinned peft without error. An "empty adapter" (random or
   zero tensors, or a file that is a copy of another artifact's adapter)
   fails here or in gate 3/4.

`timing` (never gated): eval wall seconds, baseline wall seconds.

## Acceptance oracle

The judge never trusts the artifact's own metrics. It (a) regenerates the test
set from the task definition with its own seed, (b) parses every input back to
a `datetime` with the documented template grammar (analytic inverse — no
model needed) to get the exact correct answer, (c) loads base+adapter with the
pinned transformers/peft, (d) scores exact match per row, (e) re-runs the
identical eval with the adapter detached, and (f) compares against the
recorded `metrics.json` only for the loss-curve shape rules above. An
artifact that merely "trained" without a working adapter fails 3–4; an
artifact that forged `predictions.csv` without a working adapter fails 3–4 as
well (the judge ignores `predictions.csv` content for accuracy and uses it
only for the leakage gate).

## Known-bad examples (self-test)

`judge/mutants.py` derives ≥ 8 known-bad artifacts from the known-good one by
scripted single edits / rebuilds:

1. `adapter_not_applied` — metrics.json + predictions.csv from a full run, but
   `adapter_model.safetensors` replaced by a zero-filled safetensors of the
   same names/shapes (gate 6 + 3 fail).
2. `empty_adapter` — adapter file of 4 zero bytes / header-only (gate 1/6).
3. `leakage_test_is_train` — predictions.csv inputs regenerated from the
   *train* seed (gate 2).
4. `shuffled_predictions` — predictions.csv rows kept, inputs shuffled
   (gate 2 order match; also gate 3 since content was produced in test order).
5. `no_loss_drop` — metrics.json losses replaced by a flat noisy curve
   (gate 5; accuracy gates still pass — this mutant isolates the gate).
6. `loss_spike` — losses with one epoch jump > 0.5 (gate 5 monotone-ish).
7. `predictions_wrong_format` — predictions written as raw dates like
   `March 3, 2024` instead of ISO (gate 1 regex).
8. `copy_of_train_metrics` — metrics.json `finetuned_accuracy` claims 0.95
   while adapter is zeroed (gates 3–4, recorded claims are never trusted).

`judge/selftest.sh` grades the known-good (must pass) and every mutant (each
must fail ≥ 1 gate), prints the kill rate, checks determinism (two grades of
the good artifact give byte-identical verdicts except `timing`), and exits
non-zero unless the kill rate is ≥ 90 %.

## Toolchain (pinned, sha256-checked)

`judge/setup.sh` installs into `$HOME/.venvs/gpu-lora-finetune/` exactly what
the judge needs: torch, transformers, peft, safetensors, numpy and the full
transitive closure, every package pinned and sha256-verified through pip's
`--require-hashes` mode (`judge/requirements-cpu.lock`, generated by
`judge/genlock.py`). Nothing published in the two weeks before this demo was
built. `setup.sh` is idempotent (skips when the venv already provides the
pinned versions) and refuses other platforms. `judge/VERSIONS.txt` records
what it actually installed. The GPU lease image (Python 3.13, torch
2.10.0+cu128) is used as-is for training; the judge itself runs on CPU
anywhere.

## Reproducibility

Grading is deterministic given `--seed` (two runs → byte-identical verdict
JSON except `timing`; enforced by `selftest.sh`). RECEIPT.md carries real
pasted output of setup, selftest and grade with exit codes, kill rate, key
numbers, wall times, lease ids and their deletion, plus a Deviations
section. Training is deterministic given its seed to the extent the GPU stack
allows (cuDNN benchmark off, deterministic flags on); the judge does not
re-run training — it grades the artifact.

## GPU path (lead's run)

The heavy step (training) runs on a 4 GiB VRAM slice lease created via the
agent-next REST API (exactly like `cookbook/small-gpu/run.py`):
`POST /sandboxes {"accel":{"vram_gb":4,"reserve":"exec"}}`; weights, tokenizer,
data and the peft wheel are downloaded in the CPU builder sandbox (sha256
recorded), uploaded to the lease via the files API, training runs, results are
downloaded, then `DELETE` + `GET` → 404/dead in a `finally` block. The judge
runs afterwards on CPU (or on the lease, identically). Every lease id and its
deletion are logged in RECEIPT.md.
