## README / SPEC problems found (criterion 5)

A. **`python3 run.py` fails in a fresh sandbox with no sandbox
   credentials, and the README gives no fallback.** First error (exit 1,
   0.117 s): `run.py: sbx CLI not found; install with pip install
   "git+https://github.com/agent-next/sandbox#subdirectory=cli"` — even
   right after following the README's own install line, because pip
   installs `sbx` into `~/.local/bin`, which is not on `PATH` here
   (pip's own warning: `The script sbx is installed in
   '/home/user/.local/bin' which is not on PATH`). The README never
   mentions `PATH`. Second error (exit 1, 0 s) once `~/.local/bin` is
   added: `run.py: export SBX_API_KEY (or E2B_API_KEY) first`.
   The README's "Run it" block is therefore not sufficient to run the
   demo end-to-end; the media section even documents an
   independent-run expectation (`REPRODUCE.md`) with no recipe for it
   without credentials.

B. **README wall-time table is optimistic at the top end.** Measured
   `setup.sh` = 382 s vs the README's "~140–370 s" (RECEIPT: 348 s / 366 s).
   `selftest.sh` = 254 s, inside "~120–255 s"; `grade.sh examples/good`
   = 7 s, exactly as documented. "create sandbox ~2 s" and "clone repo
   ~3 s" are not measurable without credentials.

C. **README result "boot banner at 0.085 s" is host-dependent.** Same
   firmware, same seed, same QEMU: 0.141 s here. Still 70× inside the
   10 s limit, and `grade.sh`'s gate only reports "banner within 10s", so
   the claim is not falsifiable from a verdict — only from a capture.

D. **`setup.sh` prints what looks like an error on a clean run**:
   `sudo: unable to resolve host instance: Name or service not known`
   (twice, on stderr) because the container has no hostname entry. Exit
   is 0 and everything installs, but a reader following the README sees
   it as a failure.

E. **The seed for reproduction appears only in the media caption**
   (README line 25, "`grade.sh --seed 20260814`"); the "Run it" and
   "Results" sections never state it, so a reproducer has to guess or
   rely on it being `grade.sh`'s default.

F. **Nothing in the README says how to obtain `ffmpeg`/`ffprobe`,
   `matplotlib`, or `media/data/`.** `media/make_media.sh` needs all of
   them, and `judge/setup.sh` installs none of them. With `media/data/`
   absent it fails fast, which is the correct behaviour but nowhere
   promised by the README's "`media/make_media.sh` rebuilds them all":

   ```
   make_media: missing data file /tmp/.../media/data/verdict-good.json
   ... (21 more) ...
   make_media: run media/collect_data.sh first
   EXIT=3
   ```

   (`collect_data.sh` is documented only inside `make_media.sh`'s header,
   and it takes ~8.5 min — 506 s here — which the README never mentions.)

G. **`SPEC.md`, which the README defers to for "the full rules",
   disagrees with the code in five places** (none of them changes the
   verdict for `examples/good`, but each would mislead a reproducer):

   1. `SHELL_S` default: SPEC table says **25**; `judge/grade.sh:64` sets
      **30** (and `drive.py`/`capture.py` use 30.0).
   2. Gate 3 `maps_ok`: SPEC says `.text + .rodata + .data <= 8192`;
      `judge/grade.sh:191` sums only `.text` and `.rodata`. `.data` is 0
      here, so the numbers coincide (2224 B).
   3. Gate 4 `boot`: SPEC requires QEMU "exit code 124 (timeout)"; no code
      path checks 124 — `boot` comes solely from `drive.py`'s banner
      detection.
   4. `CRVEC_CASES` / `CRVEC_MAX` are documented as "overridable on the
      `grade.sh` command line", but `grade.sh` accepts only `--seed` and
      `--json`, and `drive.py:170-173` hardcodes 12 random buffers of at
      most **64** bytes (`MAX_ARG_BYTES = 64`), so `CRVEC_MAX = 4096` is
      never exercised. The CRC gate therefore never tests a buffer over
      64 bytes.
   5. The constant is spelled `QEEMU_BIN` in SPEC; the code reads
      `QEMU_BIN` (`grade.sh:61`).

H. **Minor:** `judge/requirements.txt` is named in the README's
   "pinned" story but is a comment-only file with zero packages (correct,
   but surprising); and `media/requirements.txt` pins
   `matplotlib==3.10.5`, which installed and rendered cleanly here.

## Conclusion

The demo reproduces: every gate verdict, the 14/14 kill rate with the same
behavioural/build-only split and the same per-mutant gates, the key metrics
(46/46, 15/15, 2224 B, flash/SRAM), the determinism property, the pinned
tool versions and the sha256-verified downloads all match README.md and
RECEIPT.md within the SPEC tolerances. The two things that did not
reproduce byte-for-byte are both traceable to wall-clock values written
into artifacts, and both were proven deterministic when those values are
held fixed: `result.png` (draws `grade.sh elapsed 7s` vs 8 s) and
`demo.mp4` (typing pace from capture timestamps). The only step that could
not be executed at all is `python3 run.py` itself, blocked by missing
sandbox credentials; its three inner steps were run directly on this
sandbox instead, with matching results.
