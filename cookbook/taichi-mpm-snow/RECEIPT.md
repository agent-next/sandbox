## Hardening

### Pinned everything

`judge/setup.sh` downloads exactly nine Python wheels via
`pip install --require-hashes -r judge/requirements.txt`; every wheel
is pinned by exact version **and** sha256, so any upstream change
fails loudly at install time. No `latest` URLs, nothing auto-resolving.
`judge/requirements.txt` lists only manylinux x86_64 wheels for the
supported CPython range (3.10–3.13) plus `py3-none-any` wheels, so the
file works on every supported minor.  All pins are at least two weeks
old (the newest, Pygments 2.21.0, was published 2026-08-17; Taichi
1.7.4 was published 2025-07-31).

### Determinism

Taichi's CPU backend accumulates P2G scatter contributions through
floating-point atomics; with more than one thread the order is
non-deterministic and the verdict JSON differs at the 1e-7 level
(single-bit differences in the `py` and `vel_com_y` fields).
`examples/good/sim.py` therefore pins
`ti.init(arch=ti.cpu, cpu_max_num_threads=1, random_seed=args.seed)`,
and `selftest.sh` grades `examples/good` twice with the same seed and
compares the verdict JSON with the `timing` key removed:

```
[selftest] Determinism check (same seed twice, verdict JSON except 'timing'):
[selftest]   good  deterministic (identical)
```

## Deviations

- **Verification environment.** The standard asks for two fresh
  agent-next sandbox runs.  sandbox credentials are not available to
  the builder, so both runs were done on the local Debian 12 host with
  the virtualenv wiped in between (same effect: setup starts from
  nothing).  The one-command `run.py` is provided for a reviewer with
  `SBX_API_KEY` to re-verify in a real sandbox end to end.
- **Media.** `media/frames/` carries five real PNG frames from the
  good run (step 0, 800, 1600, 3200, 5000), upscaled 8x nearest from
  the simulation's 64x64 renders and kept far below the 300 KB cap
  (1.3–1.6 KB each).  The 20–60 s `demo.mp4`, `result.png` and
  `loop.png` are left to the later media task and intentionally
  absent.
- **Deaths of three mutants by Gate 1.** `dt_too_large`,
  `no_boundary` and `p2g_weight_bug` blow up (NaN/Inf) long before a
  later gate could trip, so the judge catches them via
  `completion` (non-finite metrics / abnormal exit).  This matches
  the brief's expectation for "dt too large (blow-up)" and the
  physical nature of the other two faults: removing the boundary or
  corrupting the P2G stencil crashes MPM outright.
